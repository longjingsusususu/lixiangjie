> 对应你给的「报销助手上线检查」：系统本体是需求汇总 + 需求管家 Agent，
> 报销语境映射为——报销数据脱敏→需求/人员信息脱敏；LLM 配额→Agent 对话与模型调用配额；

## B. 并发与限流（LLM 配额）

| # | 检查项 | 负责人角色 | 验证方法 | 通过标准 | 现状 |
|---|---|---|---|---|---|
| B1 | Agent 对话接入限流 | 研发负责人 | 同一账号 10 秒内并发 10 次 `POST /api/agent/chat`，统计 429 数；再对 `/api/chat` 做同样操作对照 | Agent 对话与员工查询台走同一限流器（当前仅 `/api/chat` 有 `check_rate`）；超阈返回 `42901` 中文提示；写操作接口阈值更低（如 3 次/10s） | ✗ Agent 对话未限流 |
| B2 | 登录暴力破解防护 | 系统管理员（秦芮）+ 研发负责人 | 脚本对 `/login` 连错 6 次同账号，再错 3 次不同账号同 IP | 连续 5 次失败后锁定 10 分钟并返回明确中文；锁定事件写 `audit_logs`；不同账号同 IP 亦有频率上限 | ✗ 登录无失败计数 |
| B3 | LLM 调用配额与降级 | 研发负责人 | 把单用户日配额临时调为 1，连续提问 2 次；观察事件流与 `agent_runs.decider` | 超配额时明确提示"已达今日模型配额，已切换规则模式"，不返回 500；`decider=rule`；配额按用户+全局两级计数 | ◐ 有异常降级，无配额计数 |
| B4 | 并发写冲突与单写约束 | 研发负责人 | 两个并发请求对同一 item 调 `create_handover`；同时压测 5 并发 `upsert_item` | 单次请求只允许一个写操作（`42902` 已有）；并发下无 `database is locked` 500；SQLite 开 WAL + `busy_timeout=5000` | ◐ 有 42902，未开 WAL/busy_timeout |
| B5 | 容量压测与单机上限声明 | 研发负责人 + 质量验收（傅景） | 基线 50 项数据，压测 30 并发读 + 5 并发写（≥10 分钟） | P95 < 1.5s、错误率 < 1%、无锁超时；压测报告写明单机上限与"超出后需换 PostgreSQL/多实例"的阈值 | ✗ 未压测 |

## 附：三条可直接跑的核验命令

```bash
# ① 密钥是否还是默认值（有输出即为不合格）
grep -rn "meeting-demo-secret" . --include=*.py

# ② Agent 对话是否被限流（10 秒内打 10 次，应出现 429）
for i in $(seq 10); do curl -s -o /dev/null -w "%{http_code} " \
  -X POST http://127.0.0.1:8011/api/agent/chat \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"goal":"双语主持相关的需求有哪些？"}' & done; wait

# ③ 审计/轨迹留痕是否齐全（三项计数应同量级，不应为 0）
sqlite3 demo.db "SELECT 'audit', COUNT(*) FROM audit_logs
  UNION ALL SELECT 'steps', COUNT(*) FROM agent_steps
  UNION ALL SELECT 'runs', COUNT(*) FROM agent_runs;"
```
