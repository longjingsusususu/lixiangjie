# 报销助手智能体系统 · 技术架构选型

约束：FastAPI（异步）· Python 3.11+ · LLM 走 API（供应商可替换）· 制度知识库向量化检索 · 两角色（员工 / 管理员）

---

## 1. 四层架构（文字版）

```
┌─────────────────────────── 入口层 ───────────────────────────┐
│  员工端 Web（问答 + 发起报销）   管理员端 Web（制度维护 + 记录）  │
│  预留：IM 机器人入口（钉钉/企微/飞书，同一套 API）               │
└──────────────────────────────┬───────────────────────────────┘
                               │ HTTPS / JWT
┌──────────────────────────────▼───────────────────────────────┐
│ 服务层（FastAPI async，无业务逻辑只做编排校验）                 │
│  · 认证与角色（JWT，user/admin）     · 会话服务（建会话/收发消息）│
│  · 报销单草稿服务（CRUD+状态机）     · 制度文档服务（上传/切分/发布）│
│  · 检索服务（向量+关键词混合召回）   · 记录与审计服务（管理员查询）│
└──────────────────────────────┬───────────────────────────────┘
                               │ 进程内调用（Provider 模式）
┌──────────────────────────────▼───────────────────────────────┐
│ 智能体编排层                                                   │
│  · 意图路由器：问答 / 建报销单 / 闲聊兜底                        │
│  · RAG 管线：切分 → 向量化 → 召回(top-k) → 重排 → 引用标注       │
│  · 工具集（function calling）：search_policy / create_draft /   │
│    update_draft / get_my_drafts（发票OCR为二期预留槽位）        │
│  · LLM 网关：统一接口屏蔽供应商差异，含超时/重试/降级/成本记账    │
└──────────────────────────────┬───────────────────────────────┘
                               │
┌──────────────────────────────▼───────────────────────────────┐
│ 数据模型层                                                     │
│  · PostgreSQL + pgvector：业务表 + 向量（一个库，运维最简）      │
│  · Redis：会话缓存 / 限流 / 排行计数                            │
│  · 对象存储（本地目录起步）：制度原文件、发票图片（二期）          │
└───────────────────────────────────────────────────────────────┘
```

三个关键选型理由：

| 决策 | 理由 | 代价与对策 |
|---|---|---|
| pgvector 而不是独立向量库 | 制度文档量级（几百~几千条 chunk）远用不到专库；少一个运维组件 | 数据涨到千万级再迁 Milvus，检索层接口已隔离 |
| LLM 网关单列一层 | "可替换供应商"是硬约束：接口差异、限流重试、成本统计都收口在这一层 | 首期只实现一个 provider，但抽象从第一天就存在 |
| 意图路由放在编排层而非提示词内 | 问答和建单是两条完全不同的链路，路由错了下游全错；规则+小模型可解释、可测试 | 后期可换成 LLM 分类，接口不变 |

## 3. 数据库表设计（PostgreSQL + pgvector）

**users — 用户**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | |
| employee_no | varchar(32) unique | 工号 |
| name / email | varchar | email 用于登录 |
| password_hash | varchar | 或对接企业 SSO，预留 |
| role | enum(user, admin) | 两角色，够用不再细分 |
| department | varchar(64) | 后续制度按部门差异化时要用 |
| is_active / created_at | bool / timestamptz | |

**chat_sessions — 会话**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid PK | |
| user_id | FK→users | |
| title | varchar(128) | 首条消息截取 |
| status | enum(active, closed) | |
| last_message_at / created_at | timestamptz | 管理员按时间查记录 |

**messages — 消息**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | |
| session_id | FK→chat_sessions | |
| role | enum(user, assistant, system, tool) | |
| content | text | |
| tool_calls | jsonb null | 编排层调了哪些工具、参数、结果摘要 |
| citation_doc_ids | jsonb null | 回答引用的 policy_chunk id，审计与"答案可溯源" |
| prompt_tokens / completion_tokens / latency_ms | int | 成本与性能统计，管理员看板用 |
| created_at | timestamptz | |

**policy_docs — 报销制度文档（文档级）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid PK | |
| title / category | varchar / enum(travel, invoice, approval, other) | 差旅标准 / 发票规则 / 审批流程 |
| version | int | 同一制度多版本并存 |
| status | enum(draft, published, archived) | 只有 published 进检索池 |
| file_path | varchar | 原文件位置 |
| chunk_count / uploader_id | int / FK→users | |
| effective_date / created_at | date / timestamptz | 制度生效时间，RAG 回答要带上 |

**policy_chunks — 制度切片（向量级）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | |
| doc_id | FK→policy_docs, ON DELETE CASCADE | 文档下架即删切片 |
| chunk_index | int | |
| content | text | 切片正文（带标题路径前缀） |
| embedding | vector(1024) | HNSW 索引（cosine） |
| token_count | int | |
| **部分唯一约束** | (doc_id, chunk_index) | |

**reimbursement_drafts — 报销单草稿**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid PK | |
| user_id / session_id | FK | 草稿与产生它的会话可追溯 |
| status | enum(draft, submitted, approved, rejected, paid) | 提交后状态机一期只到 submitted |
| currency | char(3) default CNY | 二期多币种预留 |
| items | jsonb | 行项目：日期/类型/金额/事由/发票号 |
| total_amount | numeric(12,2) | 服务端按 items 汇总，不信前端 |
| extracted_data | jsonb null | LLM 从对话中抽取的结构化字段（含置信度） |
| policy_check_result | jsonb null | 制度预检结果：通过/超标准/缺材料 + 引用的制度条款 |
| created_at / updated_at | timestamptz | |

设计要点：`items`/`extracted_data` 用 jsonb 而不是摊平成列，因为一期字段口径未冻结；`citation_doc_ids` 和 `policy_check_result` 让每个答案可溯源到制度原文——这是管理员信任系统的前提。

## 4. 第一周最小验证目标（Walking Skeleton）

**一句话：打通"员工问 → 检索制度 → 带引用回答 → 顺手生成报销草稿 → 落库 → 管理员上传新制度并发布 → 新制度立刻能被检索到"的端到端链路。**

拆成 5 天：

| 天 | 目标 | 完成标志 |
|---|---|---|
| D1 | 脚手架 + DB + 两角色登录 | docker-compose 起 postgres/pgvector+redis；JWT 登录，admin 与 user 权限隔离生效 |
| D2 | 制度入库管线 | 上传 1 份差旅制度 → 切分 → 向量化入库；重复导入幂等 |
| D3 | RAG 问答链路 | 问"出差住宿标准是多少"，回答含正确金额 + 指向原文条款的引用 |
| D4 | 报销草稿工具调用 | 对话说"我上周去北京出差打车花了 86 块"，生成 items 正确的草稿并落库，员工端可查看 |
| D5 | 冒烟测试 + 供应商切换验证 | smoke_test 全绿；**改一个环境变量把 LLM 从供应商 A 切到 B，测试仍然全绿** |

**验收判据（达不成就要调方案）：**
1. 10 个典型制度问题，8 个以上回答正确且引用准确；
2. 幻觉防线有效：问制度里没有的问题，模型回答"制度未覆盖"而不是编造；
3. 草稿端到端 < 5 秒（不含模型首 token 慢的场景）；
4. LLM 供应商切换只改配置，不改业务代码——这一条验证了"可替换"硬约束。

**第一周明确不做**：发票 OCR、真实审批流、多币种、IM 入口、性能压测。它们是二期，但目录结构和表设计已给它们留了槽位（tools.py 的 OCR 工具位、drafts 的状态机、currency 字段）。
