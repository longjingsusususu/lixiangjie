## 2. 问题结构：从九个痛点到五个失败方式

### 2.1 为什么要把 P-01~P-09 重新归并

E-01 的九个问题按"现象"列的，颗粒度不一致：P-01 和 P-02 讲的是同一件事的两面，P-06/P-07 讲的是决策链，P-08 讲的是数据缺失，P-09 讲的是访谈方法。按现象逐条做需求，会得到九个小功能，没有一个能单独验收。

改造的正确单位是**失败方式（failure mode）**——同一类失败在不同环节重复出现，只有一种解法能同时消掉它。归并后剩五个：

| 失败方式 | 定义 | 对应问题 | 发生在链路哪一段 | 是否能用 AI 解 |
|---|---|---|---|---|
| **K1 多点登记、人工比对** | 同一需求在三个环节各录一次，一致性靠人眼 | P-01 | 议程确认 / 嘉宾需求 / 供应商交接 | 部分（匹配与差异定位可，判定不可） |
| **K2 变更后无单点权威版本** | 变更走口头或群消息，执行侧仍按旧版准备 | P-02、P-05 | 嘉宾需求 → 执行 | 弱（这是规则问题，不是理解问题） |
| **K3 交接点无责任人与确认状态** | 谁录入、谁确认、确认到什么程度无书面口径 | P-03、P-04 | 五个交接节点 | 不可（必须靠卡口与签字） |
| **K4 异常无入口，只能默认通过或卡死** | 版本不明、字段冲突时没有具名接收人 | P-04、P-06 | 全过程 | 部分（分类可，处置不可） |
| **K5 输出形态不对，一线不用** | 给的是泛化摘要，一线要的是一页缺项清单 + 来源位置 | P-01、P-08 | 输出端 | 不可（这是产品形态问题） |

> 这一步不是文字游戏。K3 和 K5 恰好是价值最高、却**完全不需要模型**的两项；行业分析里六种失败模式的头号坑就是"把抽取当确认"——把 K3 误判成 AI 问题，等于用模型去替代签字，方向就错了。

### 2.2 五个失败方式的判定矩阵

判定三问：失败何时被谁看见？能否在损害前拦住？出事后能否撤销？

| 失败方式 | 何时被看见 | 能否事前拦截 | 可撤销性 | 结论 |
|---|---|---|---|---|
| K1 多点登记 | 交接时比对发现 | 能（差异清单） | 能（改回原值） | 值得做，且可先做 |
| K2 版本不同步 | 执行现场 | 能（定版 + 过期拒收） | 部分（已发出通知不可撤回） | 必须先有规则，再有工具 |
| K3 交接无确认 | **验收时才发现**（最晚） | 能（卡口阻断） | 不能（责任已模糊） | 优先级最高，且必须是硬卡口 |
| K4 异常无入口 | 出事之后 | 弱（无入口即无拦截） | 不能 | 必须先建入口，再谈智能 |
| K5 输出形态错 | **试用第一天**（最早） | 能（按清单重构） | 能（改版即可） | 成本最低、见效最快 |

### 2.3 一个必须说清的反直觉结论

按"业务价值"排序，K1/K2 最大；按"投入产出比"排序，K5 最高；按"验收能否成立"排序，K3 是唯一的前置条件。

**三者不冲突，但顺序不能颠倒**：先有 K5 的清单（否则没有判定对象）→ 再有 K3 的卡口（否则清单齐了也不算数）→ 才能谈 K1/K2 的比对与版本（否则比的是不准的清单）。

这就是本方案第 9 章实施顺序的来源，也是为什么优先级不能简单照抄 CSV 里的 P0/P1/P2——那列是"待验证假设的优先级"，原文明确写了"P0/P1/P2 不等于已完成价值风险评分"。

## 3. AI 改造清单与优先级

### 3.1 AI 改造的四条准入条件

一条改造进清单，必须四条全满足；缺一条就不做，或降级为"自动化"而不是"AI 改造"：

1. **有具名痛点**：能挂到 K1~K5 之一，且该痛点有 f 编号支撑；
2. **失败可拦截**：输出必须是人可逐条否决的候选，不允许直接落库或直接对外；
3. **失败可恢复**：错了能改回原值，且原值不被覆盖（f14）；
4. **不越过红线**：不自动确认、不自动邀请、不发布安排、不碰敏感个人需求（f05）。

> 第 2、3 条是硬门槛。T1 不满足，就是"只提醒不拦截"；第 3 条不满足，就是"模型改写原值"，两类在行业分析里都属于已验证的失败模式。

### 3.2 AI 改造项清单（9 项）

标注说明：**AI-0** = 确定性自动化，不需要模型（但属于"智能化改造"的一部分，用户感知为智能）；**AI-1** = 需要模型，人在环；**AI-2** = 需要模型且需知识库，二期。

| 编号（类型） | 改造项 | 解决的失败方式 | 输入 → 输出 | 优先级 |
|---|---|---|---|---|
| A-01（AI-1） | 需求文本结构化抽取 | K1、K5 | 群消息 / 邮件 / 表格自由文本 → 编号、类别、责任人、时间窗、确认状态**候选值** | **P0** |
| A-02（AI-0） | 跨环节同项匹配与差异定位 | K1 | 三份清单 → 疑似同项配对 + 差异字段清单 | **P0** |
| A-03（AI-0） | 变更影响面推导 | K2 | 变更前后项 + 依赖关系 → 受影响项、需重确认方、需重发范围 | **P0** |
| A-04（AI-0） | 缺项 / 未确认清单生成 | K5 | 单批次全量项 → 一页清单，四态分列（缺失 / 未确认 / 已确认 / 已定版） | **P0** |
| A-05（AI-0） | 交接三要素卡口 | K3 | 交接动作 → 三要素校验（内容清单 / 接收责任人 / 时间窗） | **P0** |
| A-06（AI-1） | 异常分类与分派建议 | K4 | 异常描述 → 类型、建议值守人、建议时限 | P1 |
| A-07（AI-2） | 已定版规则问答 | K2、K3 | 问题 → 已定版口径 + 出处；未定版 → "未定 + 找谁" | P1 |
| A-08（AI-2） | 交接单 / 客户简报生成 | K5 | 清单 + 版本 → 交接单草稿 | P1 |
| A-09（AI-1） | 会议录音 / 群消息转候选需求项 | K1、K2 | 录音转写 → 候选需求项 | P2 |

上表回答"做什么"，下表回答"错了怎么办"——这是 AI 改造能不能过验收的真正分界。

| 编号 | 人在环位置 | 主要失败方式 | 拦住它的机制 |
|---|---|---|---|
| A-01 | 逐字段采纳，原值不动 | 字段抽错、臆造责任人、把"未提"当"无" | 候选制 + 四元组来源（AI-FR-01/02） |
| A-02 | 匹配结果人工确认后才合并视图 | 漏配、误配（把两项合成一项） | 不自动合并，只出差异清单 |
| A-03 | 影响清单由协调员确认后生效 | 漏算下游、把"通知过"当"确认过" | 影响项逐条勾选，未勾不重发 |
| A-04 | 无（只读输出），一线直接使用 | 把"未确认"混进"缺失"、来源位置指错行 | 四态分列 + 可点回原文 |
| A-05 | 缺一项即不能生成交接单，无人工绕过 | 卡口被绕过、空值当已填 | 服务端一次性票据，绕过即 40405 |

### 3.4 优先级评分方法

不用"重要 / 紧急"这类主观判断，用三个可讨论的维度，各 1~3 分：

| 维度 | 1 分 | 2 分 | 3 分 |
|---|---|---|---|
| **V 价值**：能消掉的返工或外溢风险 | 只省少量书写时间 | 减少一次比对或一次重发 | 直接决定验收能否成立 |
| **I 可拦截**：失败能否在损害前被看见 | 事后复盘才发现 | 当天能被人工发现 | 系统当场阻断 |
| **R 可恢复**：出错能否改回 | 已对外发出，不可撤回 | 可改但需通知多方 | 改回原值即可 |

判定规则：

- **P0** = V≥2 且 I=3 且 R≥2，且不依赖未确认的接口 / 预算；
- **P1** = V≥2 但 I=2，或依赖 P0 先落地；
- **P2** = V=2 但 R=1，或依赖外部条件（转写质量、隐私审批）；
- **不做** = I=1，或 R=1 且涉及对外 / 写回。

逐项打分：

| 编号 | V | I | R | 判定 | 理由 |
|---|---|---|---|---|---|
| A-01 | 3 | 3 | 3 | P0 | 抽取结果只是候选，原值不动，逐字段可撤 |
| A-02 | 3 | 3 | 3 | P0 | 差异清单先给人看，不自动合并 |
| A-03 | 3 | 3 | 2 | P0 | 影响清单确认后才重发，但通知已发出不可全撤 |
| A-04 | 3 | 3 | 3 | P0 | 只读输出，改版即可 |
| A-05 | 3 | 3 | 3 | P0 | 缺项即阻断，且卡口在生成前 |
| A-06 | 2 | 2 | 3 | P1 | 误分派当天可纠，但延误已发生 |
| A-07 | 2 | 2 | 2 | P1 | 错误建议会被照做，只能靠来源与拒答约束 |
| A-08 | 2 | 3 | 3 | P1 | 草稿可核可改，价值中等 |
| A-09 | 2 | 2 | 2 | P2 | 转写质量与隐私均未验证 |

### 3.5 与 CSV 原始优先级的差异（必须说明）

CSV 给的是：REQ-1/2/3 = P0，REQ-4/5 = P1，REQ-6 = P2。本方案的一处调整：

| 项 | CSV | 本方案 | 调整理由 |
|---|---|---|---|
| REQ-4（缺项清单 + 来源位置）→ A-04 | P1 | **P0** | 它是 M6 与 AC 判定的**取数载体**：没有清单，"50 项是否具备责任人"根本无法逐项判定。同时它是唯一一线会主动用的输出（f15），采用率决定试点是否成立 |
| REQ-6（只读集成与数据质量）的一部分 → A-02 | P2 | **P0（仅字段最小集与映射）** | 三源无统一编号（f30）时，清单连"同一项"都认不出。但**只做最小集**：编号映射 + 字段规范化 + 降级 CSV，不做全量质量治理 |
| REQ-5（跨团队口径）→ 部分并入 A-02 | P1 | P1（不升） | 依赖叶书召集双方代表，是组织动作，系统只能提供对照视图 |

> 其余保持 CSV 原判。这个调整不改变任何事实，只改变施工顺序，且**不增加一期工作量上限**——A-02 的"最小集"版本比全量质量治理省，A-04 本来就是 FR-06 的一部分。

### 3.6 三个 P0 级 AI 改造的行为契约（不写代码，只写必须遵守什么）

**A-01 抽取的行为契约**

1. 输入是自由文本，输出是**候选字段**，每条候选必须带 `源工具 | 单据号 | 行位置 | 原文片段`；
2. 抽不到就返回"未确定"，**不得**用上下文推测补全，更不得填默认值；
3. 原文中"可能""待定""看情况"一律映射为"未确认"，不映射为"已确认"；
4. 抽取结果与现有值并存，采纳才写入新版本，**原值永远保留**（f14）；
5. 同一字段出现两个互相矛盾的值时，不选一个，而是两条都列出并标冲突，进人工队列。

**A-04 清单的行为契约**

1. 四态必须分列，不允许合并成"完成 / 未完成"两态——缺失与未确认是两件事（f31）；
2. 每条必须能定位到来源行，点击可回溯原文；
3. 排序按"距截止时间由近到远"，不按录入时间；
4. 空值显示为"缺失"，不显示为空白或"无"；
5. 清单本身不产生任何状态变更，纯只读。

**A-05 卡口的行为契约**

1. 三要素（内容清单 / 接收责任人 / 时间窗）任一为空 → 交接单**无法生成**，接口返回明确错误码与缺哪一项；
2. 不存在"强制通过"开关；管理员也不能绕过；
3. 生成后的交接单不可编辑，只能作废重开，作废需留原因；
4. 交接单必须打印/导出后与系统版本号一致，防止纸质与系统两张皮。

### 4.3 系统边界：三个"只有"

数据单向流动：三源（服务台 / 业务台账 / 文件库）→ 编号映射与字段规范化 → 本系统（登记 / 版本 / 清单 / 队列）→ **人工确认（具名）** → 交接签收。系统在这一条链上只做三件事，且**只做**这三件：

| 边界 | 具体表现 | 怎么证明它真的守住了 |
|---|---|---|
| **只有读** | 对三源零写入；不发消息给供应商或嘉宾；不向外部系统推送任何数据 | 抓包 + 源系统日志，写请求 0 次（AC-33） |
| **只有人能确认** | 系统可以提示"这一项缺责任人"，但填责任人与改确认状态的只能是人；模型写入恒为 0 次 | 对抗输入测试，写入 0 次（AC-27） |
| **只有具名接收人能闭环** | 异常队列的关闭需要具名人签字，不存在"超时自动关闭"或"系统判定通过" | 每条异常四字段齐全（AC-23） |

> 这三条不是设计选择，是 f05 红线的系统化表达。任何一条被突破，验收的基础就不存在了——因为 f02 要求"50 项全部具备责任人和确认状态"，而这个"具备"必须由人认定，不能由系统自称。

五态：`缺失 → 未确认 → 已确认 → 已定版 → 已交接`

| 迁移 | 允许条件 | 谁来做 | 系统能做什么 | 系统不能做什么 |

| 未确认 → 已确认 | 责任人具名确认 + 记录确认方式 | **人** | 校验责任人非空、留痕 | **不能代替确认** |

三条不会松动的规则：**不得跳态**（不能从"缺失"直接到"已定版"）、**不得回退覆盖**（作废保留原因）、**不得无主**（任一态都必须有具名责任人）。

## 6. 追溯矩阵

### 6.1 追溯链设计

追溯链是一条单向可回查的线：**事实 f → 失败方式 K → 需求 REQ/FR → AI 改造 A → 验收 AC → 指标 M**，其中每一段的证据都落在证据台账里（B 级随原始记录到位升为 A 级）。

| 段 | 从哪查 | 查到什么 | 查不到说明什么 |
|---|---|---|---|
| ① 事实 → 需求 | 需求的"来源事实"列 | 这条需求解决哪几条 f | 需求无出处，不该写进规格 |
| ② 需求 → 改造 | 需求的"失败方式 / 改造项"列 | 用什么手段解，解的是 K 几 | 需求没有解法，或解法无需求 |
| ③ 需求 → 验收 | 需求的"验收项"列 | 拿什么判它合格 | 需求不可验收 |
| ④ 验收 → 指标 | AC 表中体现的 M 编号 | 过了这条对哪个业务指标有贡献 | 验了但不产生业务价值 |

四段都要能双向查：从需求能查到它在解决哪个事实，从验收能查到它验的是哪条需求，从指标能查到它的取数来自哪个字段。

### 8.3 一句实话

## 附录 C　术语

| 术语 | 含义 |
|---|---|
| 五态 | 缺失 → 未确认 → 已确认 → 已定版 → 已交接 |
| 三要素 | 交接必须齐的三项：内容清单、接收责任人、时间窗 |
| 双时间戳 | 业务发生时间 + 系统接收时间，两者都留 |
| 双条件 | 版本有效期 + 确认状态，同时满足才算有效版本 |
| 卡口 | 不满足条件即阻断的强制校验点，无绕过开关 |
| 人在环 | 系统只出候选，采纳与确认由具名的人完成 |
| 失败方式 | 同一类失败在不同环节重复出现的最小模式（K1~K5） |
| 门禁 | 阶段之间的放行条件，不满足不得进入下一阶段 |
