2. 问题结构：从九个痛点到五个失败方式

2.1 为什么要把 P-01~P-09 重新归并

E-01 的九个问题按"现象"列的，颗粒度不一致：P-01 和 P-02 讲的是同一件事的两面，P-06/P-07 讲的是决策链，P-08 讲的是数据缺失，P-09 讲的是访谈方法。按现象逐条做需求，会得到九个小功能，没有一个能单独验收。

改造的正确单位是失败方式（failure mode）——同一类失败在不同环节重复出现，只有一种解法能同时消掉它。归并后剩五个：

失败方式定义对应问题发生在链路哪一段是否能用 AI 解
K1 多点登记、人工比对同一需求在三个环节各录一次，一致性靠人眼P-01议程确认 / 嘉宾需求 / 供应商交接部分（匹配与差异定位可，判定不可）
K2 变更后无单点权威版本变更走口头或群消息，执行侧仍按旧版准备P-02、P-05嘉宾需求 → 执行弱（这是规则问题，不是理解问题）
K3 交接点无责任人与确认状态谁录入、谁确认、确认到什么程度无书面口径P-03、P-04五个交接节点不可（必须靠卡口与签字）
K4 异常无入口，只能默认通过或卡死版本不明、字段冲突时没有具名接收人P-04、P-06全过程部分（分类可，处置不可）
K5 输出形态不对，一线不用给的是泛化摘要，一线要的是一页缺项清单 + 来源位置P-01、P-08输出端不可（这是产品形态问题）
这一步不是文字游戏。K3 和 K5 恰好是价值最高、却完全不需要模型的两项；行业分析里六种失败模式的头号坑就是"把抽取当确认"——把 K3 误判成 AI 问题，等于用模型去替代签字，方向就错了。

2.2 五个失败方式的判定矩阵

判定三问：失败何时被谁看见？能否在损害前拦住？出事后能否撤销？

失败方式何时被看见能否事前拦截可撤销性结论
K1 多点登记交接时比对发现能（差异清单）能（改回原值）值得做，且可先做
K2 版本不同步执行现场能（定版 + 过期拒收）部分（已发出通知不可撤回）必须先有规则，再有工具
K3 交接无确认验收时才发现（最晚）能（卡口阻断）不能（责任已模糊）优先级最高，且必须是硬卡口
K4 异常无入口出事之后弱（无入口即无拦截）不能必须先建入口，再谈智能
K5 输出形态错试用第一天（最早）能（按清单重构）能（改版即可）成本最低、见效最快

2.3 一个必须说清的反直觉结论

按"业务价值"排序，K1/K2 最大；按"投入产出比"排序，K5 最高；按"验收能否成立"排序，K3 是唯一的前置条件。

三者不冲突，但顺序不能颠倒：先有 K5 的清单（否则没有判定对象）→ 再有 K3 的卡口（否则清单齐了也不算数）→ 才能谈 K1/K2 的比对与版本（否则比的是不准的清单）。

这就是本方案第 9 章实施顺序的来源，也是为什么优先级不能简单照抄 CSV 里的 P0/P1/P2——那列是"待验证假设的优先级"，原文明确写了"P0/P1/P2 不等于已完成价值风险评分"。

3. AI 改造清单与优先级

3.1 AI 改造的四条准入条件

一条改造进清单，必须四条全满足；缺一条就不做，或降级为"自动化"而不是"AI 改造"：

  1. 有具名痛点：能挂到 K1~K5 之一，且该痛点有 f 编号支撑；
  2. 失败可拦截：输出必须是人可逐条否决的候选，不允许直接落库或直接对外；
  3. 失败可恢复：错了能改回原值，且原值不被覆盖（f14）；
  4. 不越过红线：不自动确认、不自动邀请、不发布安排、不碰敏感个人需求（f05）。
第 2、3 条是硬门槛。T1 不满足，就是"只提醒不拦截"；第 3 条不满足，就是"模型改写原值"，两类在行业分析里都属于已验证的失败模式。

CSV 给的是：REQ-1/2/3 = P0，REQ-4/5 = P1，REQ-6 = P2。本方案的一处调整：

3.6 三个 P0 级 AI 改造的行为契约（不写代码，只写必须遵守什么）

A-01 抽取的行为契约

  1. 输入是自由文本，输出是候选字段，每条候选必须带 源工具 | 单据号 | 行位置 | 原文片段；
  2. 抽不到就返回"未确定"，不得用上下文推测补全，更不得填默认值；
  3. 原文中"可能""待定""看情况"一律映射为"未确认"，不映射为"已确认"；
  4. 抽取结果与现有值并存，采纳才写入新版本，原值永远保留（f14）；
  5. 同一字段出现两个互相矛盾的值时，不选一个，而是两条都列出并标冲突，进人工队列。

A-04 清单的行为契约

  1. 四态必须分列，不允许合并成"完成 / 未完成"两态——缺失与未确认是两件事（f31）；
  2. 每条必须能定位到来源行，点击可回溯原文；
  3. 排序按"距截止时间由近到远"，不按录入时间；
  4. 空值显示为"缺失"，不显示为空白或"无"；
  5. 清单本身不产生任何状态变更，纯只读。

A-05 卡口的行为契约

  1. 三要素（内容清单 / 接收责任人 / 时间窗）任一为空 → 交接单无法生成，接口返回明确错误码与缺哪一项；
  2. 不存在"强制通过"开关；管理员也不能绕过；
  3. 生成后的交接单不可编辑，只能作废重开，作废需留原因；
  4. 交接单必须打印/导出后与系统版本号一致，防止纸质与系统两张皮。

4.3 系统边界：三个"只有"

数据单向流动：三源（服务台 / 业务台账 / 文件库）→ 编号映射与字段规范化 → 本系统（登记 / 版本 / 清单 / 队列）→ 人工确认（具名） → 交接签收。系统在这一条链上只做三件事，且只做这三件：

边界具体表现怎么证明它真的守住了
只有读对三源零写入；不发消息给供应商或嘉宾；不向外部系统推送任何数据抓包 + 源系统日志，写请求 0 次（AC-33）
只有人能确认系统可以提示"这一项缺责任人"，但填责任人与改确认状态的只能是人；模型写入恒为 0 次对抗输入测试，写入 0 次（AC-27）
只有具名接收人能闭环异常队列的关闭需要具名人签字，不存在"超时自动关闭"或"系统判定通过"每条异常四字段齐全（AC-23）
这三条不是设计选择，是 f05 红线的系统化表达。任何一条被突破，验收的基础就不存在了——因为 f02 要求"50 项全部具备责任人和确认状态"，而这个"具备"必须由人认定，不能由系统自称。

6. 追溯矩阵

6.1 追溯链设计

追溯链是一条单向可回查的线：事实 f → 失败方式 K → 需求 REQ/FR → AI 改造 A → 验收 AC → 指标 M，其中每一段的证据都落在证据台账里（B 级随原始记录到位升为 A 级）。

段从哪查查到什么查不到说明什么
① 事实 → 需求需求的"来源事实"列这条需求解决哪几条 f需求无出处，不该写进规格
② 需求 → 改造需求的"失败方式 / 改造项"列用什么手段解，解的是 K 几需求没有解法，或解法无需求
③ 需求 → 验收需求的"验收项"列拿什么判它合格需求不可验收
④ 验收 → 指标AC 表中体现的 M 编号过了这条对哪个业务指标有贡献验了但不产生业务价值

四段都要能双向查：从需求能查到它在解决哪个事实，从验收能查到它验的是哪条需求，从指标能查到它的取数来自哪个字段。

7. 验收标准清单

7.1 四层验收，不能混为一谈

层验什么谁判什么时候不通过怎么办
L1 桌面推演口径是否一致（不含系统）顾明岚 + 林亦舟第 0 周口径没定就不开工
L2 功能验收系统行为是否符合规格秦芮 + 傅景第 2、4 周修 + 回归
L3 规则验收规则是否被正确执行（卡口、状态机）傅景第 3 周修规则或改规格
L4 业务验收50 项是否真的可判定、一线是否真的用顾明岚 + 傅景 + 林亦舟试点末不签，或缩小范围
最常见的错误是把 L2 当 L4：功能全过、一线不用、验收照样不成立。本清单把"一线愿意继续用"（AC-42）写成硬指标，就是为了防这个。
